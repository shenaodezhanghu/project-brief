# Project Brief

一个面向 Codex 的跨项目工具仓库，包含两个彼此独立的部分：

- `project-brief` Skill：初始化时建立详细项目事实档案，让新窗口或其他模型先读 Markdown 就能理解项目；后续通过增量摘要和独立 Git 节点恢复、保存、查看和回退上下文。
- `tools/token-observer`：在本地按任务、项目和时间查看 Codex token 消耗，并显示 Codex 侧边栏中的任务名称。

## 解决的问题

- 新会话无需重新通读整个项目。
- 项目目标、验收标准、当前任务和下一步持续保存。
- 已开发很久的项目也能增量接入，不要求从头整理。
- 历史上下文按需查看，避免每次加载全部记录。
- 上下文恢复与代码回退分开，防止误操作项目代码。

## 安装

安装到用户范围，供多个项目使用：

```text
C:\Users\<你的用户名>\.agents\skills\project-brief
```

也可以只安装到一个项目：

```text
<项目根目录>\.agents\skills\project-brief
```

把仓库根目录中的 `SKILL.md`、`references`、`scripts` 和本 README 复制到上述目录。`tools` 是独立工具，不需要放入技能目录。Codex 通常会自动发现技能；若未出现，重启 Codex。

## 初始化项目

在项目根目录打开 Codex，然后输入：

```text
$project-brief 初始化
```

技能会先识别新项目或已有项目，再读取 README、配置、路线文档、目录和实际入口，建立详细项目事实档案；只对无法从证据确认且会影响后续工作的内容逐步询问。每次提供具体方案，也允许自由输入。初始化需要明确项目目标和验收标准，但不会要求用户手工罗列项目全部信息；问题在实际出现后才记录。

初始化建立：

- `PROJECT_CONTEXT.md`：详细且相对稳定的项目事实档案，包含项目身份、研究/产品主线、技术和运行链路、数据与产物、模块职责、当前方案、关键约束和按任务选择的证据路径。
- `CURRENT_TASK.md`：当前阶段、需求、进展、下一步，以及带核验时间的 Git HEAD、可用空间和近期测试等易变状态。
- `.project-brief/store`：本地独立 Git 上下文节点库。
- 项目根生效的 `AGENTS.override.md` 或 `AGENTS.md` 中的 Project Brief 受管区块：要求后续 Agent 自动读取和维护摘要。

建议把 `.project-brief/` 加入项目的 `.gitignore`。两个 Markdown 摘要可以提交到项目 Git，节点库默认只保存在本机。

## 新窗口恢复

在已经接入的项目目录中新建任务后，可以直接输入实际要求，例如“修复登录后的白屏问题”。项目规则会要求 Agent 自动读取摘要、核验相关代码并在完成改动后再次维护摘要，不需要先输入 Skill 指令。

如果只想恢复并汇报项目状态，可以输入：

```text
$project-brief 继续
```

也可以明确写成：

```text
$project-brief 继续，帮我修复登录后的白屏问题
```

普通项目要求和后一种用法都会先核验相关上下文，再在同一轮处理要求。新要求优先于历史任务；信息充分时不重复确认。

## 自动维护

项目接入后，用户不需要在每次修改后输入维护指令。Agent 应在每个会修改项目文件的任务中：

1. 开始时读取两个摘要；复杂项目先以 `PROJECT_CONTEXT.md` 作为项目全貌入口。
2. 完成实际改动和验证后，根据本轮差异更新摘要。
3. 在最终回复前完成上下文收尾。
4. 完成一个可独立恢复的需求或实质阶段时保存 Git 上下文节点。

这是通过项目根生效规则文件中的受管区块持续生效的。安装新版 Skill 后，已有项目在下一次普通任务或“继续”时会自动补装规则；如果旧摘要缺少当前任务需要的事实，Agent 会按相关证据补全，不需要重新初始化或全库重读。

整理旧版按日期追加的摘要时，Agent 先保留仍有效的独有规则和用户决定；实验过程已有报告时只在摘要留下当前结论与完整项目相对路径。方案状态区分已选方向、待冻结参数、已实现接口和已验证效果。`project-brief-detailed-v2` 只是格式标记，不能代替事实核验；恢复时只打开与本轮任务相关的证据。

## 手动维护入口

如果文件由用户、其他工具或另一个未执行 Project Brief 的会话修改，可以手动执行：

```text
$project-brief 维护
```

可以附带变更线索，例如 `$project-brief 维护，刚加入登录审计模块`。技能会核验实际文件和 Git 差异，更新或清理两个摘要；普通维护不保存节点。需要同时创建可恢复的上下文节点时使用 `$project-brief 维护并保存`。

初始化只在项目首次接入时执行一次，不需要每修改一次就重新初始化。

如果摘要文件意外缺失，`维护`会优先从最近的本地 Git 上下文节点恢复，再用当前项目证据校正；没有节点时会自动重建最小摘要并继续维护。它不会因此要求重新执行初始化。跨电脑使用且希望保留节点时，需要另行迁移 `.project-brief/store`；即使没有迁移，维护也能从当前项目重建摘要。

## 会话交接提醒

Project Brief 会在安全且确有收益的节点建议切换新会话，例如一个大阶段完成、即将进入不同阶段或发现上下文混淆。提醒不会自动执行交接。

- 用户未回应：继续当前工作，不创建新任务、不反复提醒；自动摘要维护照常进行。
- 用户确认：更新摘要并保存节点，创建接手任务，先只读核对项目和交接信息，再继续工作。
- 用户拒绝或要求稍后提醒：当前阶段不再打扰，到新的实质阶段或可靠的新压缩检查点再评估。

没有创建任务能力的宿主只提供可复制的接续指令，不虚报自动交接成功。自动压缩次数只有在宿主或可选 Hook 提供可靠事件时才使用，不由模型猜测。

## Git 节点边界

上下文节点保存两个摘要、项目代码 HEAD、已跟踪文件状态和指定证据文件的哈希。它默认不保存源码，也不会执行 `reset --hard`、`clean` 或强制推送。

- 恢复上下文前自动创建 backup 节点。
- 恢复上下文不会回退项目代码。
- 查看旧代码优先使用 `git show`、`git diff` 或独立 worktree。
- 撤销已提交代码优先使用 `git revert`，保留历史。
- 删除节点只删除节点引用，不改变当前摘要；Git 对象可能仍然存在。

节点管理脚本可独立调用，详细命令见 [references/git-nodes.md](references/git-nodes.md)。

## 设计原则

- 摘要用于导航，源码和测试才是当前事实。
- 只核验与本轮任务相关的文件，避免全库重复读取。
- 明确区分已确认事实、资料推断和待验证假设。
- 用户本轮指令优先，历史记录不构成新的操作授权。
- 有实质进展后才保存节点，不按消息频率制造历史噪声。

## Token 可视化

Token 可视化不参与 Skill 的上下文恢复，也不会增加项目摘要。它作为仓库中的独立工具维护，使用方法见 [tools/token-observer/README.md](tools/token-observer/README.md)。

在任意电脑克隆仓库后进入该目录并运行：

```powershell
python server.py
```

工具会自动寻找当前用户的 Codex 数据目录。页面中的任务名称来自当地 Codex 的 `session_index.jsonl`，因此不依赖本电脑写死的名称或路径。
