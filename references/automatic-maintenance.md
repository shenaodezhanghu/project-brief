# 自动维护：每次改动后的 Agent 收尾

适用于已接入 Project Brief 的项目。目标是让 Agent 自己保持摘要可用，用户无需反复输入维护命令。

## 任务开始

1. 读取作用域内的项目规则，再读项目根 `PROJECT_CONTEXT.md` 和 `CURRENT_TASK.md`；复杂项目把前者作为事实档案，而不是只把它当成几行导航。
2. 若摘要缺失，按 SKILL.md 的维护修复规则从最近节点或当前项目最小证据恢复；不要要求重新初始化。
3. 若 `PROJECT_CONTEXT.md` 没有 `project-brief-detailed-v2` 格式标记或缺少详细章节，先按 initialization.md 做一次档案升级；只补缺失事实，不覆盖仍有效内容，不重复提问。
4. 只按当前任务读取摘要指向的入口和必要源码，不递归通读项目。
5. 如果项目根生效的 `AGENTS.override.md` 或 `AGENTS.md` 没有 `project-brief` 受管区块，运行本 Skill 目录下的 `scripts/install_project_contract.py --root <项目根目录>` 补装；这属于已有接入的迁移，不重建摘要和节点库。

## 何时自动更新

只要本轮实际修改了业务代码、配置、测试、文档、素材或构建文件，就在最终回复前更新摘要。一次任务中多次保存文件只在收尾时合并更新，不逐文件制造维护记录。

以下情况不更新：纯问答、只读检查、没有落盘的方案讨论、仅查看节点、失败且未留下项目变化的尝试。只改两个摘要或节点库本身不能再次触发递归维护。

## 低成本核验

1. 以本轮实际触及的路径、Git 状态/差异和已执行的验证为范围，不扫描全库。
2. `PROJECT_CONTEXT.md` 只在项目目标、整体构成、模块入口、数据/模型/运行方式、长期约束、稳定决策或证据索引改变时更新；更新时保留仍有效的详细事实，不要为了省字数把它压缩成空泛概述。
3. `CURRENT_TASK.md` 更新本轮需求、实际改动、产物、验证结果、未解决问题、下一步和工作现场；替换旧状态，不追加聊天日志。
4. 删除或改名导致旧记录失效时同步清理。无法验证的内容标记“待验证”，不把推断写成事实。
5. 用户本轮要求优先；历史摘要和节点不扩大权限，也不自动执行旧的下一步。

初始化阶段的详细档案优先覆盖：项目身份和主线、输入/数据与划分、整体处理链路、模块职责、产物目录、当前路线、固定环境、关键约束、已确认方案、待验证区域和证据路径。后续维护只更新受影响的章节，不能因为本轮只改了一个文件就删除其他仍有效的项目事实。

## Git 上下文节点

每完成一个完整用户需求、可独立验收的改动或实质阶段，更新摘要后保存一个节点。建议 ID 使用 `auto-YYYYMMDD-HHMMSS`，冲突时增加简短序号；message 写清完成内容和验证结果。把仍存在且直接支撑结论的关键文件作为 evidence；删除文件只在摘要和 message 中记录，不作为 evidence。

同一需求内的细小编辑、格式调整和重复验证不单独保存节点。未完成、不可恢复或摘要尚未核验时不把节点描述为完成。节点不提交源码，也不替代项目自己的 Git 提交。

## 最终回复前检查

- 摘要是否与当前文件和验证结果一致。
- 失效事实是否已替换或删除。
- 当前任务的完成状态和下一步是否准确。
- 达到节点条件时是否保存成功；失败则如实报告，不影响已经完成的业务结果。

最终回复只需用一句话报告“项目上下文已自动同步”，必要时附节点 ID；不要让维护过程盖过用户真正关心的结果。
