# 初始化：逐步询问，兼容已有项目

入口：`$project-brief 初始化` 或 `$project-brief init`。不要求长提示词，不要求用户第一次就说明问题。这里的逐步交互是工作方式，不会自行切换应用的计划模式。

## 先看能确定的事实

检查当前目录的项目身份、适用项目规则、已有上下文文件、README、一级目录和 Git 状态。只读取定位所需信息，不递归读取源码、不全量读 Git 历史。资料能回答的问题不重复问；多个项目无法确定根目录时先询问目标项目。

记录“已有文档中的目标”“源码可验证的事实”“本轮用户确认的目标”之间的区别。已有项目的完成状态不能仅凭 README 或提交消息认定；关键能力通过相关入口/已有测试核验，未执行的验证明确标注。

## 一次一个决策

优先使用当前环境可用的交互问答工具：在计划模式可使用 request_user_input；其他模式可使用 request_user_input_async。每次呈现一个主题、2–3 个具体可选方案，工具 UI 允许自由输入，不额外列“其他”。方案应结合项目证据，说明差异，推荐项应有理由。工具返回“已接收问题”不等于用户已回答；等待回答，收到后再处理依赖该选择的步骤。等待期间可以检查独立的项目事实，不依赖超时推定确认。没有这类工具时，用简短文字逐题询问并接受自由输入。

按缺失信息逐步推进，跳过已经明确的项：

1. 接入方式。依据目录和资料判断是否已有项目；无法判断才问。已有项目可提供“接续当前阶段（推荐）”“建立整个项目的现状导航”“规划下一阶段”；新项目可提供“先明确目标和最小验收（推荐）”“梳理现有方案后确定目标”。初始化不得默认重建、重构或覆盖已有成果。
2. 目标。根据项目资料提供 2–3 个具体目标候选，允许用户自己输入。已有项目要区分整体目标与本阶段目标；以用户本轮选择为准。目标完全未知时先用自由输入问题收集，不编造候选业务目标。
3. 验收标准。将已选目标转换成可观察的完成条件，再给“最小可用”“完成当前阶段”“用户定义范围”等具体方案，每个方案写出实际交付和验证方式。没有执行的检查不能承诺已经通过。用户也可直接修改或自定义条件。

只在确实影响目标/验收时追问约束，不把技术栈、预算、工期等变成固定问卷。不要问“你的当前问题是什么”作为必答项；用户主动提出的问题可记录，但初始化不得主动生成缺陷清单或把可能风险写成已发生问题。

## 形成可持续的起点

目标和验收明确后，简短复述并继续建档；通常无需再加一次确认。存在互相冲突或必须由用户决定的含义时才提出一个针对性问题。

- 新项目：保存目标、验收、已定约束和最小起步动作；没有实现就写“尚未实现”，不用虚构模块。
- 已有项目：增量整理模块入口、已验证能力、现有决策与本阶段目标；保留已有任务 ID、有效规则和用户未提交的工作。当前阶段未知时写“待确定”，不擅自续做历史待办。
- 若暂无具体开发任务，CURRENT_TASK.md 可记录“初始化完成，等待下一项任务”，包含目标和验收；不强行创建问题栏目。
- 按 context-template.md 更新摘要，合并生效项目规则中的短入口；按 git-nodes.md 建立上下文库并保存初始化节点。已有库不重建、同名节点不覆盖。
- 最后只给目标/验收简述、保存的节点 ID 和下一条简单指令：`$project-brief 继续`。初始化授权仅涉及上下文建档，不自动开发、重构、提交源码或推送。

后续工作：用户新增需求时更新任务及验收；问题实际发生时记录复现、预期/实际、证据与处理状态；阶段完成后更新摘要并保存新节点。避免将交互过程全文存入摘要。
